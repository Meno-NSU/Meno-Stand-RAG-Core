# Контракт `meno-backend/1`: как написать стенд для Менона

Стенд — это отдельный сервис с RAG, который отвечает на вопросы про НГУ. Шлюз Менона показывает его в меню,
пересылает ему вопросы пользователей и (если стенд участвует в арене) сравнивает его ответы с другими.
Ваш код мы не читаем. Всё, что нужно, — реализовать HTTP API, описанный ниже, и пройти проверку `check-backend`.

Пример стенда на один файл: `packages/meno-contract/src/meno_contract/example_stand.py`. Его можно скопировать как
основу.

## 1. Что нужно реализовать

Три адреса (третий и первый обязательны, второй нужен только для стенда без манифеста):

| Метод и путь | Зачем |
|---|---|
| `GET /meno/v1/manifest` | Кто вы, какие LLM предлагаете, как называются ваши этапы |
| `GET /v1/models` | Необязательно; обычный список моделей в стиле OpenAI |
| `POST /v1/chat/completions` | Ответ на вопрос потоком SSE |

Транспорт: HTTP или HTTPS внутри сети НГУ. Если вы задали ключ, шлюз шлёт `Authorization: Bearer <ключ>`. Стенд не
должен быть доступен из интернета.

### 1.1. Манифест

```json
{
  "protocol": "meno-backend/1",
  "name": "RAGU",
  "description": "Необязательная подсказка",
  "version": "2026-11-09-kb36",
  "build": "a1b2c3d",
  "kb": "kb-v36",
  "llms": [
    {"id": "gemma-4-12B-it", "name": "Gemma 4", "context_length": 60000}
  ],
  "default_llm": "gemma-4-12B-it",
  "stages": {"graph_walk": {"ru": "Обход графа", "en": "Graph walk"}}
}
```

- `protocol` (обязательно): ровно `meno-backend/1`. Стенд с другим значением в меню не попадёт.
- `name` (обязательно): название для показа.
- `version` (обязательно, `[A-Za-z0-9._+-]{1,64}`): то, что соревнуется. Новое значение даёт новую строку
  лидерборда. **Меняйте его при любой смене базы знаний, пайплайна или настроек, влияющей на ответы.** Иначе новые
  ответы припишутся старой версии.
- `build` (необязательно): коммит или сборка. Сохраняется с каждым запуском, на рейтинг не влияет.
- `kb` (необязательно): подпись базы знаний для показа.
- `llms` (обязательно, не пусто): у каждой записи обязательны `id` (уникальный) и `name`. Необязательно:
  `context_length`; `requires_auth` (шлюз покажет замок гостю и откажет в запросе); `status`:
  `{"state": "available|rate_limited|unreachable", "until": "ISO-время"}`.
- `default_llm` (обязательно): один из `id` в `llms`. На нём `check-backend` задаёт вопросы.
- `stages`: подписи этапов. Обязательны для каждого имени этапа вне стандартного списка (раздел 2). Подпись из
  манифеста важнее стандартной.

Идентификатор стенда в манифесте не указывается: его назначаем мы при подключении.

### 1.2. Запрос

```
POST /v1/chat/completions
Authorization: Bearer <ключ>        если задан
X-Meno-Request-Id: chatcmpl-...     для связи логов
X-Meno-Trace: 1                     только когда шлюзу нужны детали, см. раздел 3

{"model": "<id из llms>", "messages": [...], "stream": true,
 "max_tokens": ..., "temperature": ..., "top_p": ..., "stop": ...}
```

Стенд обязан уметь только `"stream": true`. Для клиентов, просящих `stream: false`, ответ собирает шлюз. Параметры
вроде `max_tokens` можно игнорировать, если ваш пайплайн их не поддерживает.

### 1.3. Ответ: поток SSE

Заголовок ответа `Content-Type: text/event-stream`. Блоки разделяются пустой строкой. Строки-комментарии (`: ping`)
можно слать сколько угодно, например чтобы соединение не считали зависшим. Новая строка может быть `\n` или `\r\n`.

| Событие | Обязательно | Содержимое |
|---|---|---|
| `event: stage` | хотя бы один этап | `{"stage": "retrieval", "status": "started", "duration_ms": 12.5, "detail": {"lines": ["..."]}}` |
| `event: thinking` | нет | `{"content": "..."}`: рассуждения модели |
| `data:` без `event` | да | Текст ответа в формате OpenAI `chat.completion.chunk`, см. ниже |
| `event: sources` | да, хотя бы раз | `{"sources": [{"document_title": "...", "source_url": "https://...", "date": "2026-01-31"}]}` |
| `event: contexts` | только при `X-Meno-Trace: 1`, тогда обязательно | см. раздел 3 |
| `event: pipeline_trace` | нет, только при `X-Meno-Trace: 1` | см. раздел 3 |
| `event: error` | при сбое | `{"code": "...", "message": "...", "retryable": true, "retry_after_sec": 30}` |
| `data: [DONE]` | да, последним | Конец ответа |

Пример текстового блока:

```
data: {"object": "chat.completion.chunk", "choices": [{"index": 0, "delta": {"content": "Привет "}}]}

```

Правила по событиям:

- **Этапы.** Имя этапа — `[a-z0-9_]{1,64}`. Статус: `started`, `completed`, `failed`, `skipped`. Этап может
  повторяться (раунды поиска). У каждого `started` должен быть парный `completed`, `failed` или `skipped`.
  `duration_ms` и `detail` необязательны. `detail.lines` — готовые строки для показа пользователю (не больше 50 строк
  по 500 символов, лишнее обрежется): фронтенд не знает, что значат ваши детали.
- **Рассуждения** шлите только событием `thinking`. Не кладите `<think>...</think>` в текст ответа: проверка
  предупредит об этом.
- **Источники.** `source_url` должен начинаться с `http://` или `https://` (или быть пустым); `date` необязателен.
  Список может быть пустым, но событие нужно прислать хотя бы раз. Слать можно в любой момент до `[DONE]`, в том
  числе после текста. Больше 20 источников шлюз не покажет.
- **Первый токен** выдайте не позже чем за 120 с, иначе фронтенд прервёт запрос.
- **Лимиты шлюза.** Пауза между кусками потока не больше 300 с (шлёпайте `: ping`, пока думаете), весь ответ не
  дольше 900 с, текст ответа не длиннее 40 000 символов, один блок SSE не больше 1 МБ (для `contexts` и
  `pipeline_trace` до 16 МБ). При превышении шлюз обрывает ответ. `check-backend` проверяет размер блоков, длину
  текста и первый токен (120 с); паузу в 300 с и общие 900 с он не проверяет, следите за ними сами.
- Событие `summary` слать не нужно: итог считает шлюз.
- Неизвестные поля и события шлюз игнорирует.

### 1.4. Ошибки до начала потока

Обычный статус HTTP и тело `{"error": {"message": "...", "code": "..."}}`:

- 400 — неизвестная модель (код `model_not_found`);
- 429 — перегрузка (с заголовком `Retry-After`);
- 503 — стенд временно недоступен.

Пользователю шлюз покажет собственный текст по коду, а ваш `message` запишет в лог.

## 2. Стандартные этапы

Подпись в манифесте для них не нужна, фронтенд знает их сам:

`abbreviation_expansion`, `anaphora_resolution`, `query_rewrite`, `retrieval`, `fusion`, `rerank`,
`context_assembly`, `generation`.

Любое другое имя (например, `graph_walk`) обязано иметь подпись `{"ru": "...", "en": "..."}` в `stages` манифеста.

## 3. Детали запуска: заголовок `X-Meno-Trace: 1`

Шлюз (или раннер бенчмарка, обращающийся к стенду напрямую) шлёт этот заголовок, когда ему нужны подробности. Браузер
этих событий никогда не получает. Только при заголовке стенд, **после текста ответа и до `[DONE]`**:

- **обязательно** шлёт `event: contexts`:
  `{"contexts": [{"id": "...", "url": "...", "title": "...", "text": "...", "rank": 1}]}`.
  Это то, на чём реально основан ответ, в порядке использования. `id` и `text` обязательны, остальное нет. Формат не
  привязан к виду поиска: если у вас нет фрагментов, отдайте те пакеты данных, на которых строился ответ;
- **может** прислать `event: pipeline_trace`: `{"pipeline_trace": {...}}`. Шлюз понимает ключи `search_queries`,
  `system_prompt`, `user_prompt`, `dialogue_history`, `retrieved`, `fewshots`, `stage_details`, `generation_model`,
  `core_model`. Остальное сохраняется как непрозрачный след.

Без заголовка `contexts` слать нельзя.

## 4. Правила для авторов

- Стенд не хранит содержимое диалогов дольше обработки запроса. Кэш в памяти допустим, запись на диск нет: иначе
  удаление данных пользователя до него не дойдёт. В логах не должно быть текста диалогов.
- Стенд размещается на инфраструктуре НГУ.
- Дополнительный стенд на прод-сервере не занимает GPU сам: работает на CPU и обращается к общим сервисам.
- Большие прогоны бенчмарка идут на отдельный экземпляр стенда, а не на тот, что обслуживает пользователей.

## 5. Как проверить себя

Запустите свой стенд и выполните (понадобится [uv](https://docs.astral.sh/uv/)):

```
uvx --from "git+https://github.com/Meno-NSU/Meno-Stand-RAG-Core@feat/gateway-stands#subdirectory=packages/meno-contract" check-backend http://host:port
```

Если у стенда есть ключ, добавьте `--key КЛЮЧ`. Скрипт:

1. читает манифест и проверяет его поля;
2. задаёт обычный вопрос на `default_llm` и разбирает поток: этапы, их парность и подписи, текст, `sources`, `[DONE]`;
3. задаёт тот же вопрос с `X-Meno-Trace: 1` и проверяет `contexts`;
4. отправляет запрос с неизвестной моделью и ждёт 4xx.

Вывод — список пунктов `[OK]`, `[FAIL]`, `[ПРЕДУПРЕЖДЕНИЕ]`; у не пройденных написано, что исправить. Код возврата 0,
если не пройденных пунктов нет (предупреждения не мешают), иначе 1. Запускайте его сами, пока всё не станет `[OK]`.

Чтобы посмотреть на рабочий образец, запустите пример и проверьте его:

```
python -m meno_contract.example_stand --port 9100     # нужны fastapi и uvicorn
check-backend http://127.0.0.1:9100
```

## 6. Что передать нам

URL стенда (доступный из сети шлюза) и ключ, если он есть. Идентификатор стенда и название в меню мы назначаем сами.
Перед этим убедитесь, что `check-backend` печатает «Итог: стенд соответствует контракту».

## 7. Эндпоинт без манифеста

Если на `GET /meno/v1/manifest` стенд отвечает 404, шлюз считает его обычным OpenAI-совместимым эндпоинтом: берёт
список моделей из `GET /v1/models`, а название из нашей записи. Такой эндпоинт появляется в меню, но не в арене и
лидерборде, и у него нет этапов и источников. `<think>` в тексте ответа по-прежнему вырезает фронтенд.
`check-backend` для такого стенда проверяет `/v1/models`, текст и `[DONE]` и сообщает, что в арене он участвовать не
сможет (итоговый код возврата при этом 1: это напоминание, что для арены нужен манифест).

## 8. Версии протокола

Новые необязательные поля и события версию протокола не меняют, шлюз игнорирует неизвестное. Несовместимое изменение
будет называться `meno-backend/2`; какое-то время шлюз будет понимать обе. Стенд с неизвестной версией протокола в
меню не попадает.
