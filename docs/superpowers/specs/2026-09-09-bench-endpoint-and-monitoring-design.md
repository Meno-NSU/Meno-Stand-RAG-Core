# Скрытый bench-эндпоинт и мониторинг прода

Дата: 2026-09-09
Статус: дизайн утверждён, реализация не начата

## Задача

1. **Bench-эндпоинт.** OpenAI-совместимый эндпоинт для прогона бенчмарков, отдающий
   ответы вместе со всей RAG-метадатой. Доступен узкому кругу разработчиков по
   секретному токену. Публичный сайт `meno.nsu.ru` работает штатно и без изменений.
2. **Мониторинг.** Наблюдаемость веб-сервиса с ретенцией: нагрузка, латентность,
   ошибки, число пользователей — с историей, переживающей рестарты.

## Что уже есть (не переписываем)

- `POST /v1/chat/completions` уже OpenAI-совместим и уже возвращает `sources` и
  `pipeline.stages` (`src/meno_rag/api/main.py:652`).
- Полная воронка RAG уже собирается в `src/meno_rag/stand/trace.py::build_pipeline_trace`:
  переписанные запросы, dense/lexical ранги по каждому запросу, fusion-скоры,
  реранк, финальный промпт, тексты чанков. Управляется флагом `capture_trace`;
  на проде выключено (`CAPTURE_PIPELINE_TRACE=false`).
- Prometheus-инструментирование уже написано целиком (`src/meno_rag/api/metrics.py`):
  `meno_chat_requests`, `meno_chat_request_seconds`, `meno_chat_in_flight`,
  `meno_llm_calls`, `meno_llm_latency_seconds`, `meno_errors`, `meno_http_requests`,
  `meno_http_request_seconds`, `meno_admission_active/limit`, `meno_pipeline_trace`.
  Отдаётся на `GET /metrics`.
- `GET /healthz` отдаёт статус БД, Redis, устройства эмбеддера, состояние OpenRouter.

Новых метрик писать не нужно. Нужен сборщик с ретенцией и выставление наружу.

## Журнал решений

### Р1. Выставление — путь на `:443`, не отдельный порт

`https://meno.nsu.ru/bench/v1` — новый `location` на существующем vhost.

Рассматривался и отвергнут `IP:PORT`. Обоснование отказа:

- `meno.nsu.ru` резолвится в `84.237.50.35` — это одна машина и один интерфейс.
  Обращение по IP вместо имени не меняет маршрут пакетов, это выбор строки.
- `84.237.50.35` — публичный маршрутизируемый адрес. Бинд на него = публикация в
  интернет, а не ограничение сетью НГУ (README Meno-Deploy: "anyone can hit
  84.237.50.35:9012 directly"; внешний фаервол НГУ разрешающий — на 2026-06-17
  снаружи отвечали и `:9012`, и vLLM `:9022`).
- Номер порта не является ни секретом, ни правом доступа: открытый порт на публичном
  IP находят сканеры за часы.

Порт дал бы вторую заметную точку на периметре и зависимость от разрешающего
фаервола, не добавив защиты. Путь не требует новых сокетов, сертификатов и правил
на краю сети.

### Р2. Сетевое ограничение не является несущей защитой

«Только из сети НГУ» несовместимо с «работает удалённо», а удалённые разработчики
есть. Несущая защита — токен. ACL по CIDR может быть добавлен позже как сужение,
но опираться на него нельзя.

### Р3. Один процесс, не отдельный экземпляр

Bench ходит в тот же `meno-rag-api`, что и живые пользователи. Отдельный экземпляр
стоил бы ~1 ГБ RAM (938 МБ ресурсов стенда) и второй FRIDA в VRAM рядом с vLLM,
плюс риск расхождения версий кода и KB. GPU всё равно общий, так что изоляция была
бы частичной. Изоляция делается внутри процесса: свой бюджет конкурентности и
полный обход записи в продовые таблицы.

Следствие, которое надо помнить: бенчмарк конкурирует с продом за пропускную
способность vLLM. Не гонять бенчмарк и нагрузочный тест одновременно.

### Р4. Один общий токен

Круг — 2–3 человека. Именные токены с атрибуцией в логе отложены до расширения круга.

### Р5. Кастомный usage-эндпоинт не делаем

Grafana ходит в PostgreSQL напрямую как в датасорс. «Сколько людей пользуется» —
SQL-панель, а не новый роут. Ноль нового кода на бэкенде.

### Р6. Сбор метрик — локальный, без публичной поверхности

Prometheus живёт на том же хосте и скрейпит `127.0.0.1:9006/metrics` по петле.
Путь сбора данных не проходит через интернет вообще.

Это не запрещает опциональный отладочный `location /bench/metrics` за bench-токеном
(§2.2): он предназначен для ручного `curl` при разборе инцидента, а не для скрейпа,
и защищён тем же токеном, что bench-эндпоинт. Штатный сбор от него не зависит.

### Р7. Историю латентности берём только из Prometheus

Соблазн построить её на `pipeline_runs` (там есть `total_ms`, `created_at`,
`error_code`) — ловушка: запись этой таблицы сидит внутри блока `if improvement:`
(`src/meno_rag/api/main.py:1170`), то есть только для давших согласие на анализ.
Смещённая выборка неизвестного размера, смещение коррелирует с типом пользователя.

Что можно использовать:
- `conversations` / `messages` — пишутся безусловно (коммит `a65b92d`) → надёжная
  база для usage-метрик;
- `pipeline_runs` / `pipeline_stage_runs` — только для качественного анализа RAG;
- латентность и нагрузка — только Prometheus, он считает все запросы.

## Часть 1 — RAG-Core: bench-режим

### 1.1 Настройка

`BENCH_API_TOKEN: str = Field(default="", validation_alias="BENCH_API_TOKEN")` в
`src/meno_rag/config.py`. Пустая строка = фича выключена. Fail-closed: случайно
включиться не может.

Отдельно `bench_max_concurrent: int = Field(default=4, validation_alias="BENCH_MAX_CONCURRENT")`.

### 1.2 Распознавание — `src/meno_rag/api/bench.py`

```python
def is_bench_request(request: Request) -> bool:
    """True если запрос несёт валидный bench-токен. Никогда не бросает."""
```

- читает Bearer **только** из `Authorization`, `X-Auth-Token` не принимается —
  этот заголовок принадлежит JWT приложения, и смешивать два разных типа секрета
  в одном заголовке значит однажды перепутать их местами;
- сравнивает через `hmac.compare_digest`;
- пустой `BENCH_API_TOKEN` → всегда `False`.

Вызывается **до** `auth.resolve_optional_user`. Иначе bench-токен уйдёт в
`decode_access_token`, не распарсится как JWT и молча выродится в анонимный запрос.

Бэкенд перепроверяет токен, уже проверенный nginx, не из недоверия к nginx: nginx
решает достижимость, бэкенду нужен флаг для выбора поведения. Побочный плюс —
через SSH-туннель в `127.0.0.1:9006` bench-режим работает без nginx.

### 1.3 Поведение

Новый роут не создаётся. nginx отображает `/bench/v1/*` → `/v1/*`, обработчик
`chat_completions` ветвится по флагу. Так `base_url` остаётся канонически
OpenAI-совместимым.

| | обычный запрос | bench |
|---|---|---|
| `capture_trace` | по `capture_pipeline_trace` (на проде `false`) | всегда `True` |
| трейс куда | trace-БД, только при improvement-согласии | инлайн в ответ, не пишется |
| персистентность | `conversations`/`messages`/`pipeline_runs`/`sources` | пропускается целиком |
| admission | общий бюджет (256) | свой бюджет (4) |
| Prometheus | пишется | не пишется |

Обход персистентности: `_persist_success` и `_persist_failure` не вызываются при
bench. Обоснование — прогон создал бы тысячи строк без владельца, исказив лидерборд,
статистику фидбэка и нагрузочные метрики; плюс запись синтетических вопросов в те же
таблицы усложняет ответ ИБ на вопрос о хранимых данных.

### 1.4 Формат ответа

Стандартный OpenAI-объект плюс ключи верхнего уровня. `sources` и `pipeline` уже
есть; добавляется `pipeline_trace`:

```json
{
  "id": "chatcmpl-...",
  "object": "chat.completion",
  "choices": [{"index": 0, "message": {"role": "assistant", "content": "..."}}],
  "sources": [{"document_title": "...", "source_url": "..."}],
  "pipeline": {"total_ms": 3218.4, "stages": {"rewrite": 120.0}},
  "pipeline_trace": {
    "retrieval": {"per_query": [{"query": "...", "dense": [], "lexical": []}]},
    "fusion":    {"per_query": [{"query": "...", "candidates": []}]},
    "rerank":    [{"chunk_id": 8123, "score": 0.94, "rank": 0}],
    "prompt":    {"system": "...", "user": "..."},
    "chunks":    {"8123": {"title": "...", "url": "...", "text": "..."}}
  }
}
```

Источник `pipeline_trace` — существующий `outcome.trace`. Клиенты, не знающие про
эти ключи, их игнорируют, поэтому `lm-eval` / `promptfoo` / `ragas` работают как есть.

### 1.5 Стриминг

Поддерживается. Трейс уходит финальным SSE-событием тем же приёмом, что уже
применён для `sources` (`src/meno_rag/api/main.py:925`):

```python
yield sse_event("pipeline_trace", {"pipeline_trace": trace})
```

### 1.6 Admission

Второй `AdmissionController(settings.bench_max_concurrent)` в `app.state.bench_admission`.
Bench берёт слот из него. Прогон бенчмарка не может выдать живым пользователям 503.

## Часть 2 — Meno-Deploy: выставление

### 2.1 nginx

В `nginx/meno.nsu.ru.conf`, vhost `:443`:

```nginx
# /etc/nginx/conf.d/bench-token.conf — вне git, 0640, root
map $http_authorization $bench_ok {
    default            0;
    "Bearer <СЕКРЕТ>"  1;
}

location /bench/v1/ {
    if ($bench_ok = 0) { return 404; }
    proxy_pass http://127.0.0.1:9006/v1/;
    include snippets/meno-proxy.conf;
    include snippets/meno-sse.conf;
    proxy_read_timeout 600s;
}
```

- `if` + `return` — один из двух официально безопасных вариантов `if` в nginx.
- `404`, а не `401`/`403`: снаружи путь неотличим от несуществующего.
- Проксирование прямо в `:9006` мимо Express — bench не задевает фронтовую логику сессий.
- `auth_basic off` **не нужен**: пилотный гейт снят коммитом `417e8cd`.
- `proxy_read_timeout 600s` — прогоны длинные.

Rate limit (`limit_req`) намеренно не добавляется: он дрался бы с бенчмарком, который
по своей природе долбит часто. Ограничителем служит bench-бюджет admission (§1.6),
он ограничивает параллелизм — то, что действительно важно.

### 2.2 Секрет

`openssl rand -hex 32`. Живёт в двух местах: `.env` на хосте (`BENCH_API_TOKEN=`) и
`/etc/nginx/conf.d/bench-token.conf`. Скрипт `scripts/set-bench-token.sh` по образцу
существующего `set-gate-token.sh`. Fail-closed: нет map-файла → `nginx -t` падает →
reload не происходит. В git не коммитится, во фронтенд не попадает.

Ротация: поменять в обоих местах, `systemctl reload nginx` + `run_backend.sh restart`.

Опционально: `location /bench/metrics` за тем же токеном, чтобы можно было curl'ить
сырые метрики удалённо при отладке.

## Часть 3 — Meno-Deploy: мониторинг

```
                        ┌─ Prometheus (127.0.0.1:9090, ретенция 90д)
127.0.0.1:9006/metrics ─┤     ↑ scrape 15s
                        │  node_exporter (127.0.0.1:9100)
                        └─→ Grafana (127.0.0.1:3000) ──┐
PostgreSQL (view, read-only роль) ─────────────────────┘
                                                        ↓
                                     nginx /grafana/ (auth_basic + логин Grafana)
```

**Все три сервиса строго на loopback.** Это прямой урок открытых `:9012` и `:9022`:
на этом хосте бинд в `0.0.0.0` означает публикацию в интернет.

### 3.1 Prometheus

systemd-юнит, `--web.listen-address=127.0.0.1:9090`,
`--storage.tsdb.retention.time=90d`. Скрейп `127.0.0.1:9006/metrics` каждые 15с.

Оценка объёма: ~1500–2000 серий при текущем наборе меток → примерно 1–2 ГБ на 90
днях. Свободное место проверить до установки.

### 3.2 node_exporter

`--web.listen-address=127.0.0.1:9100`. Включён намеренно: заполненный диск — самая
частая причина отказа такого сервиса, и ни одна прикладная метрика её не покажет.

Экспортер GPU (`dcgm-exporter`) отложен: полезен, но vLLM живёт отдельно от этого
стека, это самостоятельная задача.

### 3.3 Grafana

systemd, `http_addr = 127.0.0.1`, `root_url` с префиксом `/grafana/`.

Доступ: `location /grafana/` с `auth_basic` (отдельный realm, свой htpasswd) плюс
собственный логин Grafana — два независимых рубежа. Токен в `Authorization: Bearer`
для браузерного UI не подходит, поэтому механизм отличается от bench-эндпоинта.

Альтернатива без публичной поверхности: `ssh -L 3000:127.0.0.1:3000 meno`.

### 3.4 PostgreSQL — доступ только к фактам, не к содержимому

```sql
CREATE VIEW usage_conversations AS
    SELECT id, user_id, guest_session_id, created_at FROM conversations;

CREATE ROLE meno_grafana WITH LOGIN PASSWORD '...';
GRANT SELECT ON usage_conversations TO meno_grafana;
```

Grafana физически не может прочитать `messages.content`. Это сильнее, чем
«мы аккуратно написали SELECT», и это формулировка, которую можно показать ИБ:
у дашборда нет доступа к содержимому диалогов, только к фактам о них.

Утверждение подлежит проверке, а не декларации: после создания роли выполнить от её
имени `SELECT content FROM messages LIMIT 1` и убедиться, что приходит
`permission denied`. Новая роль в PostgreSQL не получает SELECT на таблицы
автоматически, но `PUBLIC` имеет `USAGE` на схему `public`, поэтому проверить надо
фактически, а не по рассуждению.

Роль создаётся вручную, как `meno_rag` (см. историю деплоя) — приложение её не создаёт.

### 3.5 Дашборды и алерты

Панели (Prometheus): RPS по провайдерам, p50/p95/p99 `meno_chat_request_seconds`,
латентность по этапам из `meno_llm_latency_seconds`, `meno_errors` по кодам,
`meno_admission_active` против `limit`, HTTP-роуты, CPU/RAM/диск.

Панели (PostgreSQL): DAU по `created_at` + `DISTINCT user_id`, доля гостей против
зарегистрированных, диалоги по дням, сообщений на диалог. История доступна задним
числом — Postgres копил её всё это время, в отличие от Prometheus, который начнёт
считать с момента установки.

Алерты: `up == 0`; рост `meno_errors`; p95 латентности выше порога;
`meno_admission_active / meno_admission_limit > 0.8`; диск > 85%; `/healthz` = `degraded`.

## Декомпозиция

Дизайн один, реализация — две независимые части в разных репозиториях, с отдельными
планами и PR:

- **План A (RAG-Core):** часть 1 — bench-режим и тесты. Не меняет публичного поведения.
- **План B (Meno-Deploy):** части 2 и 3 — выставление и мониторинг. Не требует
  изменений кода бэкенда.

План B в части bench-локации зависит от плана A (проксировать не во что, пока нет
bench-режима); в части мониторинга — не зависит ни от чего и может идти параллельно.

## Предусловия

1. **Влить `chore/open-public-remove-gate` в `main` в Meno-Deploy.** Коммит `417e8cd`
   (снятие пилотного гейта) есть только на ветке. `main` всё ещё содержит закрытый
   гейт, и деплой с `main` молча отрежет пользователей от публичного сайта. Ветвиться
   для нашей работы можно только после влития.
2. Проверить, не утекают ли метрики уже сейчас:
   `curl -s -o /dev/null -w '%{http_code}\n' https://meno.nsu.ru/metrics`.
   Если `200` — Express имеет catch-all прокси на бэкенд, и это отдельная утечка
   (имена моделей, адреса эндпоинтов, объёмы трафика, коды ошибок).
3. Проверить свободное место под TSDB.
4. `APP_HOST=127.0.0.1` в прод-`.env` подтверждён (в `example.env` стоит `0.0.0.0`).

## Тестирование

RAG-Core:
- юнит `is_bench_request`: валидный токен / невалидный / пустая настройка / нет
  заголовка / токен как `X-Auth-Token` не принимается;
- юнит: bench-admission независим от продового, исчерпание одного не влияет на другой;
- интеграция: bench-токен → `pipeline_trace` в ответе, ноль новых строк в БД;
- интеграция: без токена → обычный ответ, `pipeline_trace` отсутствует;
- интеграция: bench-запрос возвращает трейс при глобально выключенном
  `CAPTURE_PIPELINE_TRACE`;
- интеграция: стриминговый bench-запрос отдаёт событие `pipeline_trace`;
- регресс: существующий набор на обычном пути зелёный.

Замечание: на macOS полный прогон сегфолтится при наличии faiss — локально гонять
подмножество, полный набор в CI.

Meno-Deploy:
- `nginx -t` в `deploy.sh` (fail-closed при отсутствии map-файла);
- ручная проверка: `curl` с токеном → 200, без токена → 404;
- проверка, что `/` и `/v1/` отвечают ровно как до изменений.

## Риски

- **Утечка токена = полный доступ** к GPU и биллингу OpenRouter. Митигация: узкий
  список держателей, передача не через мессенджеры, ротация при смене состава.
- **Один токен на всех** — нет атрибуции в логе, отзыв у одного ломает доступ всем.
  Принято осознанно при круге 2–3 (Р4).
- **Бенчмарк конкурирует за vLLM** с продом (Р3). Не совмещать с нагрузочным тестом.
- **Деплой с `main` в Meno-Deploy вернёт гейт** до выполнения предусловия 1.

## Порядок выката

1. Влить снятие гейта в `main` (Meno-Deploy).
2. RAG-Core: bench-режим, тесты, PR, мёрж, `run_backend.sh restart` на хосте.
   На этом шаге эндпоинт доступен только через SSH-туннель — публичной поверхности ещё нет.
3. Meno-Deploy: токен на хосте, `location /bench/v1/`, `deploy.sh`. Проверить 200/404.
4. Meno-Deploy: Prometheus + node_exporter, убедиться в скрейпе.
5. Meno-Deploy: PG view и роль, Grafana, дашборды, `location /grafana/`.
6. Алерты.

Порядок обратим на каждом шаге: 2 не меняет публичного поведения, 3 добавляет один
`location`, 4–6 — отдельные сервисы на loopback.
